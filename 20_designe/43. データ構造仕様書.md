## **3. 撮影制御方法**
撮影制御方法はファイル、通信時はjson形式とする。  
ソフトウェア内部で参照するときは構造体として扱う。  
撮影制御方法には以下がある。  
- 夜間撮影
- 太陽直接撮影(朝)
- 太陽直接撮影(夕)
- 日中
- 月の影響の対処

撮影制御方法は Capture Controll Method の略で ccm をキーワードとする。  
### **3.1. 共通の定義**
#### **3.1.1. 露出設定**
■iso感度、シャッター速度、F値の三つ組。  
撮影制御方法の露出設定や限界値の指定に使用する。  
露出設定は**カメラから取得した設定値の「文字列」**で保持・通信・ファイル保存・カメラ指示をおこなう。  
カメラの表示値は切れのいい数字で実際の値とは微小にずれるため、**表示とカメラ指示は文字列、露出計算は実数**で使い分ける。  
内部の露出計算では文字列を直接使わず、「[3.1.1.1 設定可能値テーブル](#3111-設定可能値テーブル)」で対応する APEX 値(実数, 1/3段刻み)に変換して用いる。  
exposure  
jsonと構造体のメンバーを同じ名前とする。  
|名前|型|説明|
|---|---|---|
|iso|string|iso感度のカメラ設定値(例 "100","3200")|
|ss|string|シャッター速度のカメラ設定値(例 "1/4000","8","Bulb")|
|fn|string|F値のカメラ設定値(例 "1.4","16")|

##### **3.1.1.1. 設定可能値テーブル**
カメラの設定値(文字列)と露出計算用の APEX 値(実数)を対応付けるテーブル。  
テーブルの作り方は仕様書(10) §4.2 に従う(設定値の段数を求め、±0.15 に収まる 1/3 段刻みの APEX 位置に当てはめる)。  
**撮影開始時にカメラから設定可能な iso/ss/fn を取得して作り直す**。編集画面では出荷時設定/マスタの値で仮テーブルを用意する。  
1要素 expoEntry  
|名前|型|説明|
|---|---|---|
|value|string|カメラ設定値(文字列)。カメラ指示・表示・スライダー選択に使う|
|apex|double|対応する APEX 値(iso=Sv, fn=Av, ss=Tv)。1/3段刻みの正確な値。露出計算に使う|

exposureTable は iso/ss/fn それぞれの expoEntry の配列を保持する。  
露出設定(exposure)の iso/ss/fn 文字列は、このテーブルの value のいずれかと一致させる(スライダーで配列から選択する)。

#### **3.1.2. 露出設定項目**
■露出設定を変更する優先度を表す項目。  
enum class で持つ。値は規定しない。変わっても良い。  
exposureType  
|名前|値|説明|
|---|---|---|
|iso|0～|iso感度|
|ss|0～|シャッター速度|
|fn|0～|F値|

#### **3.1.3. 撮影制御方法を区別する名称**
■撮影制御方法を区別する名称。  
ccmType
enum class で持つのが良い。  
値は0は無効、それ以外は意味のある数値とする。  
enum なので規定しない。変わっても良い。  
|名前|値|説明|
|---|---|---|
|invalid|0|無効|
|night|1～|夜間撮影|
|sunrise|1～|太陽直接撮影(朝)|
|sunset|1～|太陽直接撮影(夕)|
|day|1～|日中|
|moon|1～|月の影響への対処|

#### **3.1.4. 撮影制御方法の基本クラス**
すべての撮影制御方法は ccmBase からの派生とする。  
露出設定（iso/ss/fn）の明暗限界と優先度はすべての撮影制御方法が保持するため基本クラスに持つ。  
固定露出など限界を使用しない撮影制御方法でも保持する。  
|名前|型|説明|
|---|---|---|
|ccmType|ccmType|撮影制御方法を区別する名称|
|name|string|ユーザーが定義した名称|
|limitBright|exposure|露出設定の明るい側の限界（iso/ss/fn 上限）。UI表記は「暗所限界」（暗い場所向け＝多く光を取る設定）|
|limitDark|exposure|露出設定の暗い側の限界（iso/ss/fn 下限）。UI表記は「明所限界」（明るい場所向け）|
|priority|exposureType[3]|露出設定を変更する優先度（上位から変更）|
|initial|exposure|露出の基準(iso/ss/fn。データ上のキー名 initial は維持)。§4.4 最初の補正の起点・§4.5 往復対称の基準(home)。日中=明所限界/中間点/暗所限界から選択、朝日/夕日=明暗いずれかの限界、夜間=固定露出。後方互換: 旧 initialBright(bool) があれば true→limitDark / false→limitBright で派生|
|hysteresis|double|この撮影制御方法だけの露出平滑化ヒステリシス[段]。0=全体設定(§5.10)に従う。現状は朝日/夕日のみ UI で設定(出荷時 0.3)、他は 0|
|movingAverage|ushort|この撮影制御方法だけの露出平滑化移動平均フレーム数。0=全体設定(§5.10)に従う。現状は朝日/夕日のみ UI で設定(出荷時 3)、他は 0|

注: UIの「暗所限界＝limitBright」「明所限界＝limitDark」は、限界が指す向きが「露出（明るさ）」か「撮影場所の明るさ」かで対応が逆になる。データ構造名は露出側の明暗で命名している。

注（色）: 撮影制御方法の色は **個々の撮影制御方法ではなく全体設定（§5.11）で型ごとに共通管理** する（文字色・背景色）。
撮影計画の色・各撮影制御方法の初期値・撮影計画固有の撮影制御方法の各画面で、タイトルバーの背景色/文字色に用いる。
（エッジ端末転送用に ccm へ背景色を派生値として載せる場合があるが、ユーザーは型ごとの全体設定で編集する。）

### **3.2. 夜間撮影**
ccmNight  
ccmBase からの派生。  
固定露出のため limitBright と limitDark に同じ値（固定露出値）を設定する。  
出荷時設定の固定露出値は iso=1600、ss=8、fn=1.4 とする。  
jsonと構造体のメンバーを同じ名前とする。  
固有のメンバーを以下に示す。  
|名前|型|出荷時設定|説明|
|---|---|---|---|
|sunAltitude|double|-18.0|開始終了の太陽高度。単位10進数の「°」|
|autoEdge|bool|true|開始終了の自動判別をおこなう|
|postNightEv|double|0.0|夜間後移行(§3.9)の目標露出補正。範囲 -5.0～+5.0、1/3刻み|
|preNightEv|double|0.0|夜間前移行(§3.7)の目標露出補正。範囲 -5.0～+5.0、1/3刻み|

### **3.3. 朝日撮影**
ccmSunrise  
ccmBase からの派生。  
日の出時刻に太陽を直接撮影するための撮影制御方法。自動露出でおこなう。  
露出設定の明暗限界と優先度は基本クラス（limitBright/limitDark/priority）を使用する。  
太陽高度は「撮り始め(sunAltitude)」～「終わり(sunAltitudeEnd)」の範囲で指定する（UIは2つまみの範囲スライダー、+6°～-18°）。朝日は昇るため終わりが明るい側。  
jsonと構造体のメンバーを同じ名前とする。  
固有のメンバーを以下に示す。  
|名前|型|出荷時設定|説明|
|---|---|---|---|
|sunAltitude|double|-6.0|撮り始めの太陽高度。単位10進数の「°」|
|sunAltitudeEnd|double|0.0|終わりの太陽高度。単位10進数の「°」（0°=太陽中心が地平線）|
|ev|double|-3.0|露出補正。範囲 -5.0～+5.0、1/3刻み|

### **3.4. 夕日撮影**
ccmSunset  
ccmBase からの派生。  
夕日を直接撮影するための撮影制御方法。  
薄明の時系列が「朝日撮影」と逆になるだけで構成は同等とする。  
メンバーは「朝日撮影(ccmSunrise)」と同じ。太陽高度の範囲スライダーは朝日と左右が逆（夕日は沈むため始まりが明るい側）。  
|名前|型|出荷時設定|説明|
|---|---|---|---|
|sunAltitude|double|0.0|撮り始めの太陽高度。単位10進数の「°」|
|sunAltitudeEnd|double|-6.0|終わりの太陽高度。単位10進数の「°」|
|ev|double|-3.0|露出補正。範囲 -5.0～+5.0、1/3刻み|

jsonと構造体のメンバーを同じ名前とする。  
固有のメンバーを以下に示す。  
|名前|型|出荷時設定|説明|
|---|---|---|---|
|ev|double|0.0|露出補正。初期値は±0|

### **3.6. 月の影響への対処**
ccmMoon  
ccmBase からの派生。  
夜間撮影中に月が画角に入る、もしくは近くにある場合の露出設定への対処を定義する。  
時間帯によって挿入されるものではない。  
露出設定の明暗限界と優先度は基本クラスを使用する。  
ただし autoBrightness では暗所限界(limitBright)は夜間撮影の固定露出値で固定とし（UIではグレーで移動不可）、ユーザーは明所限界(limitDark)のみを設定する。保存時 limitBright には夜間撮影の値を書き込む。  

#### **3.6.1. 対処方法の種別**
moonMode  
enum class で持つ。値は規定しない。変わっても良い。  
|名前|値|説明|
|---|---|---|
|none|0～|補正しない|
|autoBrightness|0～|画角全体の明るさで自動補正をする|
|moonExposure|0～|月自体を撮影する目的で月に露出を合わせる|

#### **3.6.2. 月の影響への対処**
jsonと構造体のメンバーを同じ名前とする。  
固有のメンバーを以下に示す。  
|名前|型|出荷時設定|説明|
|---|---|---|---|
|mode|moonMode|none|対処方法の種別|
|startLuminance|double|0.0|自動補正を開始する撮影対象の輝度。範囲 0～+3ev（autoBrightness 用）|
|ev|double|0.0|目標の露出補正。範囲 0～-10ev（autoBrightness 用）|
|initialExposure|exposure|―|開始時露出設定（moonExposure 用）|
|atmosphericExtinction|bool|false|大気消光補正をおこなう（moonExposure 用）|
|extinctionCoef|double|0.2|大気消光係数。範囲 0.1～0.6|
|geocentricCorrection|bool|false|地心距離補正をおこなう（moonExposure 用）|
|skyBrightnessCoef|double|100|月周辺の空の明るさ補正の係数。範囲 0～100[%]|

#### **3.6.3. 月の影響への対処の初期値**

`/asset/ccmPresets.json` に型キー(`night` `sunrise` `sunset` `day` `moon`)ごとの ccm 配列で保持する。
```

```
各 ccm は §3 の撮影制御方法(名称 name を含む)。初回は撮影制御方法の初期値(§7.6。**コード上の出荷時設定**＝

（撮影計画作成時に優先プリセットで初期化し、後から一覧で選び替える連携は別途実装する。）

## **6. エッジ端末との通信**
### **6.1 基本的なデータ形式**
エッジ端末との通信に使用するデータ形式なのでEdge Terminal Paketの略でetpを略号とする。  
#### **6.1.1 パケット書式**
数値のデータはリトルエンディアンとする。  
|名前|型|値|説明|
|---|---|---|---|
|header|ushort|0x8080|ヘッダ|
|cmd|ushort|可変|コマンドコード|
|method|ushort|可変|ヘッダ|
|length|ulong|可変|dataの長さ。0も可。4の整数倍|
|data|可変|可変|必要に応じたデータ|
|terminal|ulong|0x01234567|終端コード|
|sum|ulong|可変|headerからの4バイトごとの2の補数|

#### **6.1.2 method**
「[パケット書式](#611-パケット書式)」の method の値。  

etpMethod  
|名前|値|説明|  
|---|---|---|
|get|1|データの取得の要求|
|put|2|データを設定する|
|post|3|動作の要求|
|delete|4|削除の要求|
|ack|100|成功の応答|
|nak|200|失敗の応答|

#### **6.1.3 cmd**
「[パケット書式](#611-パケット書式)」の cmd の値。  
etpCmd
|名前|値|説明|  
|---|---|---|
|search|1000|検索|
|action|1|撮影開始|
|stop|2|撮影停止|
|progress|3|撮影中の進捗|
|direction|4|方位、仰角|
|capturePlan|5|撮影計画|
|controlMethod|6|撮影制御方法|
|time|7|現在時刻の設定(エッジ端末のRTC同期)|
|nameBmp|8|計画名のビットマップ(スマホ→エッジ)|
|research|9|継続=カメラ未検出時の即再探索(スマホ→エッジ)|
|cameraInfo|10|オンラインカメラ情報の通知(スマホ→エッジ)|

#### **6.1.4 チェックサムとフレーミング**
- 数値はリトルエンディアン。`sum` は header から terminal までを 4 バイトごとの符号なし 32bit 値として総和し、その 2 の補数を格納する（`sum` まで含めた全体の総和が 0 になる）。4 バイトに満たない端数は 0 で埋めてから加算する。
- TCP はストリームのため、受信側は `header`(0x8080) で同期し、`length` から 1 パケットの全長を確定して切り出す。`terminal`(0x01234567) と `sum` で妥当性を検証し、壊れていれば nak を返して再同期する。
- `data` 部はすべて UTF-8 の JSON とし、key は本仕様書 各章の構造体メンバ名を用いる。

### **6.2 トランスポートとポート**
|用途|プロトコル|ポート|役割|
|---|---|---|---|
|検索(search)|UDP ブロードキャスト|50505|スマホが送信、エッジ端末が応答|
|転送・制御・進捗|TCP|50506|エッジ端末がサーバ、スマホがクライアント|

### **6.3 検索シーケンス(UDP)**
1. スマホ → ブロードキャスト `255.255.255.255:50505` へ `etp{cmd=search, method=get, data=空}` を送る。  
2. エッジ端末 → 送信元へユニキャストで `etp{cmd=search, method=ack, data=edgeInfo}` を返す。  

edgeInfo(JSON)
|key|型|説明|
|---|---|---|
|name|string|エッジ端末の名称(43 §5.4 edgeTerminal.name)|
|ip|string|エッジ端末のIPアドレス|
|port|ushort|制御用TCPポート(既定 50506)|
|model|string|機種名(例 "M5Stack CoreS3")|
|fw|string|ファームウェア版|
|state|int|現在の撮影状態(hgeState。全セッションの集約値)|
|sessions|array|実行中セッションの一覧(最大16件。下表)。エッジで何が走っているかを検索応答1発で伝える|

edgeInfo.sessions の各要素(JSON)
|key|型|説明|
|---|---|---|
|id|string|撮影計画のid(§7.6.2。スマホから capturePlan で転送した id と同一)|
|state|int|そのセッションの撮影状態(hgeState。3=CAPTURING/7=WAITING/8=NOCAMERA 等)|

### **6.4 制御シーケンス(TCP)**
スマホがエッジ端末(`ip:50506`)へ接続し、以下を順に送る。各要求にエッジ端末は `ack`(成功) / `nak`(失敗) を返す。
|cmd|method|data|説明|
|---|---|---|---|
|time|put|{"datetime":"YYYY-MM-DDThh:mm:ss","utcOffsetMin":int}|エッジ端末のRTCと時計を設定する|
|capturePlan|put|"計画id	" + cs(自己完結JSON, §4.5)|撮影計画を転送する(ccmListに撮影制御方法を内包)。エッジは id ごとに計画を蓄積する|
|controlMethod|put|ccm(JSON, §3)|撮影制御方法を個別に転送する(任意)|
|action|post|計画id(空=旧互換: 単一計画)|指定計画の撮影を開始する。既に実行中なら nak(INVALID_STATE)|
|stop|post|計画id(空=旧互換: 全体停止)|指定計画の撮影を停止する|
|progress|get|計画id(空=集約)|進捗を取得する。ack data に下表。**計画id指定時はそのセッションの状態/進捗**(1エッジ複数カメラで計画別に取得する。該当セッションが無ければ state=IDLE)。空は従来の集約スナップショット(生存確認・復元の初期問い合わせ用)|
|direction|get|(空)|現在の方位/仰角を取得する。ack data に {"azimuth":double,"elevation":double}|
|cameraInfo|put|オンラインカメラ配列(下表)|スマホが発見中のオンラインカメラ情報を通知する(任意時点・複数可)。エッジは既知IPテーブルを更新する。送信元はスマホの**常駐プレゼンスマップ**(§5.4。撮影開始時に加え、待機中にカメラがオンライン化/IP変更した時点でも送る)|

progress の ack data(JSON)
|key|型|説明|
|---|---|---|
|state|int|撮影状態(hgeState)|
|frame|int|現在フレーム番号|
|total|int|総フレーム数|
|remainSec|int|残り秒|
|elapsedSec|int|経過秒|
|ccm|string|適用中の撮影制御方法名|
|iso|ushort|直近のiso感度|
|ss|double|直近のシャッター速度|
|fn|double|直近のF値|

cameraInfo の data(JSON, オンラインカメラの配列。各要素)
|key|型|説明|
|---|---|---|
|serial|string|カメラのシリアル番号(本人確認キーの一部)|
|model|string|カメラの機種名(本人確認キーの一部)|
|ip|string|現在のIPアドレス(ヒント。エッジは接続時に (model, serial) で本人確認する)|
|online|bool|オンライン(true) / オフライン(false)|

本人確認はIPではなく (model, serial) の複合で行う。シリアル番号はモデル内一意が限界のため、モデルも併せて確認する。IPはDHCPで変わり得るためヒントとして扱う。  

cs の JSON は §4.5 の全メンバ(place/camera/lens/interval/azimuth/elevation/landscape/events/ccmList)を含む自己完結形式とする。ccmList の各 ccm は §3 の型ごとの固有メンバを含み、`type` で判別する。

### **6.5 エッジ常時スイープ(生存監視とエッジ側操作の同期)**
スマホは撮影の有無に関わらず約30秒ごとに §6.3 の検索(UDPブロードキャスト)を行い、応答した各エッジについて次を実施する。
1. **生存/IP追従**: 応答があればオンライン。応答の ip で登録一覧の last-seen IP を更新する(DHCPのIP変動追従)。UDPは取りこぼし得るため、連続2回無応答の登録エッジは last-seen IP へ TCP(progress, data=空)で生存確認し、それも不応答ならオフラインと表示する(●=オンライン/○=オフライン)。
2. **セッション同期**: 応答の edgeInfo.sessions(§6.3)とスマホの表示状態を突き合わせる。
   - エッジで実行中なのにスマホが追跡していない計画 → 表示へ**採用**(エッジ側ローカル開始・再起動後の自動再開の検出。以降の進捗詳細は §6.4 progress の計画別ポーリングで追従)。
   - スマホが追跡中なのに sessions に無い計画 → 表示から**除去**(エッジ側停止・撮影完了の検出)。
   - スマホ側で開始/停止操作の途中(要求送信〜結果確定)の計画には触れない(操作経路との競合防止)。
   - sessions キーの無い応答(旧ファームウェア)はセッション同期を行わない(生存/IP追従のみ)。
- 撮影中の進捗表示(フレーム数等)は従来どおり約10秒間隔の progress(計画id指定)ポーリングが担い、スイープは「発見と表示状態の同期」を担う役割分担とする。
- 後から電源を入れたエッジも次のスイープで自動的にオンライン表示・実行中計画の表示に反映される。エッジがAPモード(§8)で別ネットワークにいる間はスイープでは検出できない(許容)。

## **7. データの保持・永続化**
### **7.1 区分**
保持するデータは性質で3区分する。  
- マスタ：サーバーから取得する参照用データ(カメラ一覧・レンズ一覧)。再取得可能でバックアップ不要。  
- ユーザー資産：ユーザーが作成・編集したデータ(所持カメラ・所持レンズ・場所・エッジ端末・撮影制御方法プリセット・撮影計画プリセット・全体設定・露出平滑化)。バックアップ対象。  
- 撮影計画(cs)：自己完結した撮影単位。バックアップ対象であり、エッジ端末への転送単位でもある。  

### **7.2 出荷時設定**
出荷時設定はファイルではなくコード上に保持する。  
読み込み失敗時やリセット時の最終的なフォールバックとして使用する。  

### **7.3 マスタの扱い**
カメラ一覧・レンズ一覧はマスタ(サーバ取得・再取得可)として `/master/cameras.json`・`/master/lenses.json` に保持し、変更しない。  
マスタの初期実体は `30_refer/10_機材マスター/camera_body_list.json`・`lenses_list.json`(提供済み)を用いる。  
ユーザーが追加したカメラ・レンズはマスタとは別(`/asset/ownedCameras.json` 等)に保存し、読み込み時にマージする。  
マスタは失われても再取得できるためバックアップ対象としない。  
マスタのレコード書式は §5.8/§5.9 に示す(内部の camera/lens 構造へマップして使う)。  

**インストール同梱**: サーバが未用意の現段階では、マスタはアプリに同梱して配布する。  
Android では `40_src/90_Target/20_Android/app/src/main/assets/master/cameras.json`・`lenses.json`(`30_refer` の改名コピー)を同梱し、  
初回起動時に `getExternalFilesDir(null)/master/` へコピーする(既に存在すれば残す)。これにより同梱(assets)とデータ領域(`/master`)に同じ実体が置かれ、dataManager は `/master` 経由で読む。  
将来サーバ更新を実装する際は、データ領域側(`/master`)を上書きする。  

**接続時のシリアル/フレンドリ名の自動保存**(§5.2 拡張): カメラ接続時(検索・手動接続・撮影開始)に、  
device descriptor から取得済みの serialNumber/friendlyName を、モデル一致の所持カメラ(§5.5)へ保存する。  
一致する所持カメラが無ければマスタ(モデル名一致)と device から所持カメラを自動作成して保存する。  
これにより、カメラ1台のユーザーは機材登録をしなくても接続だけで所持カメラが用意される。  

### **7.4 撮影計画**
撮影計画は1計画につき1ファイルで保存する。  
保存・読み込み・エッジ端末への転送はいずれも1計画単位でおこなう。  
エッジ端末への転送は「[6.エッジ端末との通信](#6-エッジ端末との通信)」の capturePlan を計画単位で使用する。  

### **7.5 破損対策**
- 書き込みは一時ファイルへ書いてから rename で差し替えるアトミック書き込みとする。  
- 保存時に直前の正常版を退避(.bak)し、読み込み失敗時は .bak、次に出荷時設定の順でフォールバックする。  
- 各ファイルにスキーマ版数を持たせ、旧版は読み込み時に変換(マイグレーション)する。  

### **7.6 ファイル名称・フォルダ構成**
保存はカテゴリ別にフォルダを分ける。ユーザー定義の名称(計画名・プリセット名・場所名等)は
**ファイル名に使わない**。ファイル名は ASCII の ID とし、表示名は JSON 内の `name` に持つ
(FAT/LittleFS の禁止文字・長さ制限・文字コード・重複衝突を避けるため)。

#### **7.6.1 フォルダ構成**
|フォルダ|内容|区分(§7.1)|
|---|---|---|
|`/master/`|`cameras.json` `lenses.json`|マスタ(サーバ取得・再取得可)|
|`/asset/`|`places.json` `ownedCameras.json` `ownedLenses.json` `edges.json` `ccmPresets.json` `planPresets.json` `settings.json` `capturing.json`(§7.7.1) `recvPlans.json`(§7.7.2。エッジ端末のみ) `knownCams.json`(§7.7.3。エッジ端末のみ)|ユーザー資産・状態(各カテゴリ1ファイル)|
|`/plan/`|`plan_<id>.json`|撮影計画(1計画1ファイル。§7.4)|
|`/log/`|`hg_YYYY-MM-DD.log`|動作ログ(§8)|

保存先のルートはプラットフォームが決める(§8.1 と同様、osFile が吸収する)。

#### **7.6.2 ID(時刻ベース)**
個別ファイル(撮影計画など)の `<id>` は作成時刻から `yyyyMMdd-HHmmss` とする。
- 例: `plan_20260611-153012.json`
- RTC/時計が同期済みであることを前提とする(エッジ端末は §6 の time で同期)。
- 同一秒に複数作成して衝突する場合は末尾に2桁連番 `-NN` を付す。例 `plan_20260611-153012-02.json`。

#### **7.6.3 共通規約**
- フォルダ名・ファイル名は **ASCII のみ**。
- ユーザー資産はカテゴリごとに1ファイル(中身は配列)とし、要素の識別・表示は JSON 内の `id`/`name` でおこなう。
- 書き込み・退避・版数は §7.5(`*.tmp`→rename、`*.bak`、`version`)に従う。
- 動作ログは §8(日付ごと `hg_YYYY-MM-DD.log`)に従う。

### **7.7 撮影実行状況の永続化と再起動時の再開**
電源断やアプリ再起動の後でも撮影を継続できるよう、撮影の「実行意図」をファイルに保持する。
保存ルートはプラットフォームが決める(osFile が吸収。エッジ=SD/LittleFS、スマホ=外部ファイル領域)。

#### **7.7.1 `capturing.json`(撮影実行状況)**
- 場所: `/asset/capturing.json`。中身は「撮影中であるべき」撮影計画 id の配列。例 `["20260630-071701"]`。
- **何も撮影していないときは空配列 `[]` を残す**(ファイルは削除しない＝「撮影なし」を明示する)。
- 更新規則(瞬断・失敗では消さず「意図」を残す):
  - 撮影開始で id を**追加**。
  - ユーザーによる**明示停止**で id を削除。
  - 撮影窓の**終了後にアイドル(=完了)**した計画の id を削除。
  - **失敗(ERROR)・カメラ接続断・予期せぬ電源断・シャットダウンでは削除しない**(再起動時に再試行するため)。
- 再開: 起動時にこのファイルを読み、各 id について**撮影窓内なら撮影を再開**する。撮影窓が既に終了している/計画ファイルが無い id は削除する。
  - **エッジ端末**: WiFi 接続後に実行する(カメラを SSDP で探すため、起動直後では見つからない)。
  - **スマホ(Android)**: アプリ起動時(onCreate)に実行する。エッジ経由の計画はエッジ側が自身の `capturing.json` で再開し、スマホは状態問い合わせで表示を復元する。

#### **7.7.2 `recvPlans.json`(エッジ端末: 受信した撮影計画)**
- 場所: `/asset/recvPlans.json`(**エッジ端末のみ**)。中身はスマホから受信した撮影計画 id の配列。
- エッジ端末は**この集合に含まれる計画だけ**をリスト表示する(自身の固定計画等は出さない)。計画本体は §7.4 の `/plan/plan_<id>.json` に保存される。
- 受信時(§6 `capturePlan`)に追加・保存し、削除(リストのゴミ箱)で除去・保存する。**再起動後も受信済み計画の表示を復元**する。

#### **7.7.3 `knownCams.json`(エッジ端末: 前回接続成功カメラの直結ヒント)**
- 場所: `/asset/knownCams.json`(**エッジ端末のみ**)。中身は接続・本人確認に成功したカメラの配列。
  各要素は `{"serial","model","ip"}`(発見の**IP直結ヒント**。§カメラ発見の再設計 §3.3 tier1「前回IP直結」)。
- エッジは接続成功のたびに該当 serial の要素を更新・保存する(`noteConnected`)。起動時(`hge_init`)に読み込み(`loadPersisted`)、
  無人再起動後の auto-resume でも**スマホのプッシュ無しで前回IPへ直結**できるようにする。
- **IPはあくまでヒント**。次回接続時に CCAPI `deviceinformation` の `(model, serial)` で必ず本人確認し、一致しなければ採用しない
  (IPがDHCPで変わって別カメラになっていても誤接続しない)。取りこぼした場合は通常のSSDP発見へフォールバックする。

## **8. 動作ログ**
撮影制御が正しく行われたかを後から検証するためのログ。本番運用でも使用する。

### **8.1 保存方針**
- 取得・保存は dataManager を介しておこなう。プラットフォーム差はファイル抽象(osFile)が吸収する。
- 保存先:
  - エッジ端末(M5Stack): microSD を優先、無ければ内蔵フラッシュ(LittleFS)。ディレクトリ `/log`。
  - スマホ(Android): アプリの外部ファイル領域 `.../files/log`。
- 追記オープン。書き込みは1レコード単位で flush し、撮影中に電源断しても直前までは残す。

### **8.2 ファイル名**
日付ごとに1ファイルとし、ローカル日付で `hg_YYYY-MM-DD.log` とする。  
日付が変わったら次のレコードから新しいファイルに切り替える。

### **8.2.1 起動時のログ整理(世代管理)**
ストレージ(特にエッジ端末の microSD/内蔵フラッシュ)を使い切らないよう、**起動時に古いログを自動削除**する。  
- `/log` 内の `hg_*.log` のうち**当日以外**のファイル数を数え、**5件以上**あれば名前(=日付)の古い順に削除し、**当日以外は最新4件まで**残す(当日ファイルと合わせ最大5件)。  
- 当日の判定はローカルTZでおこなう(Android=端末TZ、エッジ端末=NVS永続のTZオフセット)。当日のログは削除しない。  
- 実装は dataManager(`pruneOldLogs(offMin)`)。エッジ端末は `setup()`、Android は `onCreate` の初期化時に呼ぶ。

### **8.3 レコード書式(可変長テキスト)**
1レコードは1行(末尾の改行 `\n`)の**可変長**テキスト。先頭は固定フォーマット部「time | lvl | event」までで、それ以降の body はイベントごとの自由形式とする。区切りは `|`。  
行頭が必ず `YYYY-MM-DD HH:MM:SS` で始まるので、改行区切りで各レコードを独立に読める。SHOT のみ frame〜lum を使うため body を列整形し、その他のイベントは frame〜lum を使わず body を event 直後へ左詰めで置く。  

固定フォーマット部(time / lvl / event)。各列は左詰めで桁を揃え、区切りは `|`。event の後ろの `|` 以降が body。
|名前|幅|内容|
|---|---|---|
|time|19|`YYYY-MM-DD HH:MM:SS`(ローカル時刻)|
|lvl|3|`INF` / `ERR`|
|event|6|イベント種別(下表)|

body(イベント別の自由形式)
- **SHOT**: frame〜lum を使うため列整形する → `frame|iso|ss|fn|lum|detail`。frame=番号(右詰5)、iso(右詰5)、ss(左詰11 例 `1/4000`/`8`)、fn(左詰6 例 `16.0`)、lum=明るさ[段](右詰8 例 `+6.029`)、detail=適用中ccm名(自動補正時は `Y=<リニア輝度> ev<段差>` を付加)。
- **SHOT 以外**(START/STOP/PLAN/CCMSW/NET/ERR/INFO): frame〜lum は使わず、body を event 直後へ左詰めで置く。

event 種別
|値|body|
|---|---|
|START|計画名・開始/終了時刻|
|STOP|(なし)|
|PLAN|計画概要(間隔/方位/仰角)、および各撮影制御方法ごとに「適用区間 / iso・ss・fn の明所限界・暗所限界・基準 / 露出補正の目標ev」|
|SHOT|1枚撮影(frame/iso/ss/fn/lum と適用中ccm)|
|CCMSW|撮影制御方法の切替(旧→新 のccm名)|
|NET|IPアドレス(接続カメラ・自端末IP・エッジ端末IP等)|
|ERR|エラー(コード・メッセージ)|
|INFO|その他|

### **8.4 記録するタイミング(§6 の制御と対応)**
- 撮影の開始/停止(START/STOP)。
- カメラ接続・自IP・エッジ端末IPの確定時(NET)。
- 1枚撮影ごとの露出設定(SHOT)。
- 適用する撮影制御方法が切り替わった時(CCMSW)。
- エラー発生時(ERR)。
