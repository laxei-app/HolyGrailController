### **1.3 方針**
holyGrailタイムラプス撮影のコアとなる部分は Entity 部に実装する。  
また、ネットワークやファイルへのアクセス部分もこちらにまとめる。  
プラットフォームに依存しない共通部分には #ifdef などプラットフォームごとに分岐するコードは書かない。  
プラットフォームごとに異なる部分は同一名の別クラスとして実装する。  
全体をライブラリとして実装する。  
M5Stackは言語が同じなので同一のプロジェクトとしてビルドすることも可能である。  
しかし、UI のために必要なライブラリを変更することで Entity部のコードへの影響が出ることを避けるためこちらも独立したスタティックライブラリとして実装する。  
holyGrailEntity.cpp に UI とのインターフェースをまとめる。  
今後必要となるクラスが出てきたら躊躇なく追加する。  
特にネットワーク系の処理で UI が固まることの無いように応答を待つような機能はノンブロックで実装する。  
また、逆に entity 部から UI 側への通知で entity部がブロックされることの無いように通知を受け取ったら極力短時間で関数は終了する。  
実質的な処理は別スレッドで処理するような作りとする。  
entity部が UI に依存する事の無いようにコードを書く。  
すべてentity部が依存される形式にすること。  
entity 部からの通知は call back を登録することでおこなう。  
プラットフォームやOSに依存する部分は entity 部のプラットフォーム依存部に隠ぺいする。  
また、UI部で使用する同様の機能は UI 部に隠ぺいする。  
UI と Entity 部にまたがった使い方はしない。

### **2. Entity部**
Holy Grail Entity を意味する hge を名前空間にする。  

### **2.1 UIインターフェース概要**
Entity 部と各プラットフォームの UI(Android=Kotlin、iPhone=Swift、Windows/M5Stack=C++)との境界を定義する。  
境界は C++ の名前/型がプラットフォームをまたいで安定するように **`extern "C"` の C-ABI** で公開する。  
公開窓口は `holyGrailEntity.h`(宣言) / `holyGrailEntity.cpp`(実装) に集約する。  

設計原則は以下とする。「[1.3 方針](#13-方針)」に準拠する。  
- 依存方向は UI → Entity の一方向。Entity は UI に一切依存しない。  
- すべての境界関数は **即座に return** する。ネットワークや撮影ループなどの長時間処理は Entity 内のワーカースレッド(ossc)で実行し、結果は通知コールバックで返す。  
- 通知コールバックは Entity 側のワーカースレッドから呼ばれる。UI 側は自身の UI スレッドへ処理を委譲し、コールバック関数自体は極力短時間で return する責務を負う。  
- 通知で渡される文字列バッファは呼び出し中のみ有効であり、所有権は Entity にある。UI 側は必要ならコピーする。  
- エラーは errCode(errorCode.h) を `int32_t` で返す。  
- 命名は関数を `hge_` プレフィクス、enum を `HGE_` プレフィクスとする。  

### **2.2 データ受け渡し規約**
データ量と頻度に応じて受け渡し方法を使い分ける(ハイブリッド)。  
- 複雑・低頻度なデータ(撮影計画 cs、撮影制御方法 ccm、設定値、デバイス一覧)は **UTF-8 の JSON 文字列**で受け渡す。JSON の key はデータ構造仕様書(43)の構造体メンバー名と一致させる。  
  引数形式は `const char* json, int32_t len`。  
- 単純・高頻度なデータ(進捗、状態、エラーコード)は **プリミティブ**で受け渡す。  
- 将来の大容量データ(ライブビュー画像など)は **生バッファ(ポインタ＋長さ)**で受け渡す。現状の境界では使用しない(ヒストグラム等は Entity 内で処理する)。  

取得系(getter)は次のバッファ規約とする。  
- `(char* buf, int32_t* inoutLen)` を取り、buf が null もしくは容量不足なら必要バイト数を `*inoutLen` に格納し `ERR_HGC_BUF_SHORT` を返す。  
- 容量が十分なら書き込み、実バイト数を `*inoutLen` に格納し `ERR_HGC_OK` を返す。  
- ※ `ERR_HGC_BUF_SHORT` を errorCode.h に追加する。  

### **2.3 通知**
Entity から UI への通知は単一のコールバックに集約し、イベント種別とペイロードで区別する。  

通知コールバック型。  
```c
typedef void (*hgeNotifyCb)(int32_t event, const char* json, int32_t len, void* user);
```

通知イベント種別。  
hgeEvent  
|名前|値|説明|JSONペイロード|
|---|---|---|---|
|HGE_EV_STATE|1|状態変化|`{"state":int}`(hgeState)|
|HGE_EV_PROGRESS|2|撮影進捗|`{"frame":int,"total":int,"remainSec":int,"elapsedSec":int}`|
|HGE_EV_CAPTURED|3|1枚撮影完了|`{"frame":int,"iso":int,"ss":double,"fn":double,"luminance":double}`|
|HGE_EV_DEVICE|4|デバイス検出結果|device一覧(uuid/model/manufacturer/serialno の配列)|
|HGE_EV_SCHEDULE|5|スケジュール更新|撮影計画 cs(43 §4.5)|
|HGE_EV_ERROR|6|エラー|`{"code":int,"msg":string}`|

撮影状態。  
hgeState  
|名前|値|説明|
|---|---|---|
|HGE_ST_IDLE|0|待機|
|HGE_ST_SEARCHING|1|デバイス検索中|
|HGE_ST_READY|2|撮影準備完了|
|HGE_ST_CAPTURING|3|撮影中|
|HGE_ST_STOPPING|4|停止処理中|
|HGE_ST_ERROR|5|エラー|

### **2.5 撮影シーケンス**
画面「330.撮影計画設定」「400.撮影中」を例にした基本フロー。  
1. UI 起動時に `hge_init()` → `hge_setNotify()` で通知を受け取れるようにする。  
2. 「330.撮影計画設定」で撮影計画を確定し `hge_setPlan(id, csJson)` で保存、`hge_selectPlan(id)` で撮影対象にする。  
3. 撮影開始操作で `hge_captureStart()` を呼ぶ。即 return し、状態は HGE_EV_STATE(CAPTURING) で通知される。  
4. 「400.撮影中」では HGE_EV_PROGRESS / HGE_EV_CAPTURED を受けて進捗を表示する。  
5. 撮影停止操作で `hge_captureStop()` を呼ぶ。HGE_EV_STATE(IDLE) で完了を受ける。  
6. アプリ終了時に `hge_term()`。  

### **2.6 内部マッピング**
- `holyGrailEntity.cpp` が extern "C" 関数を受け、nlohmann/json で cs/ccm/設定を内部型へ変換し、cameraController / captureRunner を駆動する。  
- captureRunner を別スレッドで動かし、撮影ループから進捗を notify する(現状 captureRunner はスタブ、今後実装)。  
- デバイス一覧は device(device.h) の必要項目を JSON 化して HGE_EV_DEVICE で通知する。  

### **2.7 MVP範囲**
開発ステップ「Android スマホでEOS-R10を使った HolyGrail 撮影が行える」(画面330+400、開始/停止のみ、固定データ)で必要となる最小サブセットは以下。  
- 関数：`hge_init` / `hge_term` / `hge_setNotify` / `hge_setPlan`(固定JSON可) / `hge_selectPlan` / `hge_captureStart` / `hge_captureStop` / `hge_getState`  
- 通知：HGE_EV_PROGRESS / HGE_EV_STATE / HGE_EV_ERROR  

デバイス検索・設定取得・エッジ端末連携は後続ステップで追加する。
