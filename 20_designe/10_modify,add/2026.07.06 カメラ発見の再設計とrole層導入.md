# **カメラ発見の再設計と Entity「role層」導入 仕様書**

作成日: 2026.07.06  
関連: 47. モジュール構造仕様書 / 43. データ構造仕様書 / commit 444ee48・eba42ce(branch `fix/edge-msearch-retry-drop-knownip`・未プッシュ)  

## **1. 概要**

カメラ発見(ネットワーク上のカメラの検出と接続先IPの特定)の方式と、それを実装するソフトウェア構造を再定義する。  
設計と仕様を本書に併記する。まず再設計に至った不具合・不都合の経緯を述べ、続いて発見アーキテクチャ、ソフトウェア構造(role層の導入)、仕様の要点、移行方針、未決事項の順に定義する。  
本書は 47. モジュール構造仕様書 の方針(Entity=共有C++、プラットフォーム差は同名別クラス、共通部に #ifdef を書かない、iPhone拡張予定)に準拠・拡張する。  

### **1.1 用語**

- **Entity部** … HolyGrailEntity。プラットフォーム非依存の C++ コア。名前空間 `hge`。  
- **役割(role)** … 装置としての役割。「スマホ役」と「エッジ役」の2つ。OSとは別の軸。  
- **本人確認** … 接続したカメラが計画の指定カメラ本人かを確かめること。キーは `(model, serial)`。  
- **プレゼンスマップ** … スマホが常時保持する「オンラインのカメラ一覧」。  

## **2. 経緯(不具合・不都合)**

2026-07-05 のエッジ2台同時撮影の実機調査で、カメラ発見まわりに複数の問題が判明した。スマホ直結との同時刻・同ネット比較で原因の層を確定した。  

### **2.1 実機で判明した不具合(修正済み)**

**(1) エッジのSSDP発見が間欠的に不能(真因=ポート1900のバッファ溢れ)**  
エッジのM-SEARCHクライアントが `beginMulticast(239.255.255.250, 1900)` で 1900 に bind していたため、混雑LANでは1900に全機器の周期NOTIFYマルチキャストが殺到し、ESP32/lwIP の小さいUDP受信バッファが溢れてカメラのユニキャストM-SEARCH応答を取りこぼしていた。  
スマホ(Android)は ephemeral ポート(`sin_port=0`)に bind するため常に成功していた。エッジも ephemeral ポート(`begin(0)`)へ変更して解消した(commit 444ee48)。実機で `found=2` / 両カメラ `init OK` を実証した。  

**(2) エッジ2台同時で撮影が始まらない(真因=内部DRAM不足による xTaskCreate 失敗の握りつぶし)**  
`ossc::threadNet` が `xTaskCreatePinnedToCore` の戻り値を確認しておらず、内部DRAM枯渇でタスク生成に失敗しても非nullハンドルを返し、撮影runnerの `loop()` が起動しないまま establish 不発になっていた。  
2台=撮影runnerタスク×2(各16KBスタック)が内部SRAMに収まらず `r=-1` で失敗した(1台では成功していたため「1台が限界」に見えた)。切り分けは、割当は成功する(`[SEQdiag]`)が runner が起動しない(`[LOOPdiag]` が出ない)で特定した。  
軽量スレッド(netThreadワーカー・SSDP待受)のスタックを 6KB / 4KB に削減して内部SRAMを空け、撮影runner×2を確保した(commit eba42ce)。xTaskCreate 失敗の検出・ログ・nullptr返しも追加した。両カメラ CAPTURING、フレーム独立進行(R10=27/480, R100=22/480)を実証した。  

### **2.2 見えた本質的な課題**

- エッジ(ESP32)は発見を全力でやらせるのが不利である。タスクスタックはPSRAM不可で内部SRAM(約320KB)を WiFi/BLE/lwIP 等と奪い合い、UDP受信バッファも小さく、SoftAPのマルチキャスト転送も弱い。  
- スマホのSSDPは信頼できる(本調査で実証)。RAM・電波に余裕があり、DRAM制約もない。  
- SSDP一本化は脆い。#62 で既知IP直結フォールバックを廃止したため、IP到達可でもSSDPが黙ると詰む。  
- 発見が遅い。2セッションの発見を直列化し、毎回3回のM-SEARCHを行い、`found=2` が揃うまで複数ラウンドを要する。起動から両CAPTURINGまで時間がかかり撮影窓の頭を食う。  
- 無人運用の要件と緊張する。エッジの価値は「スマホの電源を切っていてもスケジュール時刻にエッジ単独で撮影開始・復帰できる」ことにあり、発見をスマホ専任にするとこれが崩れる。  

### **2.3 ソフトウェア構造上の不都合**

発見の振る舞いがスマホ役とエッジ役で分かれる。現行構造は 10_common(共有) と 20_platform(OS固有) の2層である。  
これまでは M5Stack=エッジ / Android=スマホ で OS軸と役割軸が1対1だったため platform 一層で足りていた。  
iPhone を追加すると Android と iPhone は同じ「スマホ役」であり、役割コードを platform 下に置くと同一ロジックが二重配置になる。2層では役割軸を表現できない。  

## **3. 発見アーキテクチャ(設計方針)**

### **3.1 識別子(本人確認キー)**

- IPは「ヒント」、`(model, serial)` を「本人確認キー」とする。接続後に CCAPI `deviceinformation`(`productname` と `serialnumber`)を読み、計画カメラの (model, serial) と両方一致した時のみ採用する。片方でも異なれば拒否する。  
- serial 単独は用いない。シリアル番号は「モデル内で一意」が限界で、別モデル間で同一シリアルがあり得るため、(model, serial) の複合で実質グローバル一意とする。  
- UUID(SSDPのUSN)は用いない。値は実質MAC由来でSSDP経由でしか得られず、SSDP脱却方針と相性が悪い。  
- モデル比較は既存 `camModelMatchesDev`(`stripMaker` でメーカー接頭辞を正規化)を流用する。serial が取得不能な個体は本人確認不可として自動採用しない。  

### **3.2 スマホ役: 常駐プレゼンスマップ＋プッシュ**

- 起動時に M-SEARCH で一覧を構築し、以後 NOTIFY を常時受信して最新化する(online化・IP変更を反映)。所持カメラに一致した個体は serial を自動設定する(現行「接続時シリアル自動保存」の延長)。  
- マップは presence(見えているか)のみ保持し、CCAPIセッションは張らない(占有しない)。待機中にユーザーが他用途でカメラを使ってよい、という方針と整合する。マップはオンライン/オフライン表示のソースでもある。  
- カメラの状態が変わるたび(撮影開始要求時・撮影開始待ちの間・NOTIFYでオンライン化した時点、いつでも)、`(serial, model, ip, online)` をエッジへプッシュする。IP変更も NOTIFY→プッシュで吸収する。  
- presence(見えた全部)と owned(所持登録)は分離する。LAN上の全カメラを勝手に所持登録しない(他人のカメラや :8080 の別機器が混じるため)。  
- 失効管理は `last-seen` ＋ TTL ＋ 定期M-SEARCH で行う(byebye を出さない機器が多いため)。  

### **3.3 エッジ役: 既知IPテーブル＋IP直結＋自力フォールバック**

- 能動M-SEARCHを発見の主役から外す。スマホのプッシュと前回成功IPのキャッシュで既知IPテーブル(serial→ip)を持ち、撮影は IP直結＋(model,serial)検証で行う。  
- スマホ不在時(無人)の自力フォールバックを多層で持つ。  
  1. 前回IPへ接続＋検証(最速。大半はこれで済む)。  
  2. M-SEARCH 1発(ephemeral化で使用可能。1パケットで全カメラ)。  
  3. 限定サブネットの :8080 バッチ探索(ARP/ping で実在ホストを一括で洗い出し、応答IPのみプローブ)＋検証。  
  4. APモードは 1〜3 を要さない。エッジがDHCP元締めのため接続局一覧(`apClientIps`)を読むだけで自己完結する。  
- 受動NOTIFYは「当たれば速い」従属手段とする。混雑LANでは受信も1900バッファ溢れの弱点を共有し、AP時はSoftAPマルチキャストが弱いため、主役にはしない。取りこぼしても周期再送で最終的に拾える保険として置く。  
- 「カメラ先・エッジ後(エッジを後から電源ON)」は、CCAPIのHTTP:8080が常時応答する性質を利用し、1→2→3で決定論的に発見できる。この場合 NOTIFY待受はむしろ弱い(参加時のNOTIFYを取りこぼす)。  

### **3.4 AP / STA の役割整理**

| モード | 発見の主体 | 手段 | SSDP |
|---|---|---|---|
| STA | スマホ(在時)＋エッジ自力(不在時) | プッシュ / 前回IP→M-SEARCH→限定スイープ | 補助 |
| AP  | エッジ | DHCP接続局列挙(`apClientIps`)＋:8080プローブ | 不要 |

### **3.5 サブネット探索のコスト(設計上の注意)**

/24(255.255.255.0)は実質254アドレスである。素朴に順次pingすると分単位となり実用外である(不在ホストがARP/接続タイムアウトを食うため)。  
- 順次・長タイムアウト: 約4〜10分。順次・短タイムアウト(300ms): 約75秒。バッチ並行: 約2〜5秒。前回IPヒット: 数十ms。  
- したがって全/24順次は最終手段とし、「一括ARP/pingで実在ホストのみ洗い出し→応答IPのみ:8080プローブ」でバッチ化する。探索範囲はエッジ自身の割当IPとネットマスクから自動判明する(ルーター設定は不要)。「DHCPプールに絞る」は任意最適化であり必須ではない。  

## **4. ソフトウェア構造: Entity への role層 導入**

### **4.1 変動の2軸**

変動は2軸である。OS軸(Android / iPhone / M5Stack)と役割軸(スマホ役 / エッジ役)。iPhone 追加で Android と iPhone が同じスマホ役となり、2層では役割軸を表現できない。  

### **4.2 フォルダ構成(決定: `30_role` を `10_common` と同階層に新設)**

```text
40_src/20_HolyGrailEntity
├─10_common          … 純粋共有ロジック＋抽象IF(net:: / ossc:: / osfile:: 等)
│                       ＋発見の低レベル素材(deviceDiscovery, detectSsdpBase,
│                         cameraController, connectManual, apiCanonCCAPI)
├─30_role            … ★新設: OS非依存・役割別の“振る舞い”
│   ├─10_phone       …   スマホ役: 常駐プレゼンスマップ, M-SEARCH+NOTIFY常時,
│   │                     エッジへプッシュ, serial自動設定(Android/iPhone共通)
│   └─20_edge        …   エッジ役: 既知IPテーブル, 受信プッシュ反映,
│                         IP直結+検証, 自力フォールバック
├─20_platform        … OS固有プリミティブ“だけ”(socket, thread, fs,
│   │                   multicastlock, BLE, timer)
│   ├─10_M5Stack
│   ├─20_Android
│   ├─30_iPhone      …(将来)
│   └─40_windows
└─80_test
```

### **4.3 依存の向き(内向き固定: ポート＆アダプタ)**

- 依存は `platform →(実装)→ common の抽象IF ←(呼ぶ)← role` の内向き一方向とする。  
- `30_role/10_phone` は `10_common` と抽象IF(`net::` / `ossc::` 等)のみに依存する。Android/iPhone の実体は include しない。これにより Android と iPhone が同一ソースを共有できる。  
- OS差が必要な役割機能(例: Android の MulticastLock、iPhone のマルチキャスト entitlement、M5Stack は no-op)は、抽象IFに口を追加し各 platform が実装する(例 `net::multicastHold()` / `release()`)。役割コードは口を呼ぶだけでOS差を意識しない。  
- 47. モジュール構造仕様書 §1.3 の方針「共通部に #ifdef 分岐を書かない / プラットフォーム差は同名別クラス」を踏襲・拡張する。  

### **4.4 ビルド結線**

各成果物は「core ＋ 自分の役割 ＋ 自分のOS」を選択してビルドする。  
- M5Stack(PlatformIO): `10_common` ＋ `30_role/20_edge` ＋ `20_platform/10_M5Stack`。phone役は含めない(エッジに不要コードを載せない)。  
- Android(CMake/NDK): `10_common` ＋ `30_role/10_phone` ＋ `20_platform/20_Android`。  
- iPhone(将来 Xcode): `10_common` ＋ `30_role/10_phone` ＋ `20_platform/30_iPhone`。  

### **4.5 配置ルールの言い換え(今後の指針)**

`20_platform` には「OS固有プリミティブ」だけを置く。複数OSにまたがる「役割の振る舞い」は `30_role/<役割>` に OS非依存で置く。役割コードは抽象IF経由でのみOSに触れる。  

## **5. 仕様の要点**

### **5.1 ETP拡張: カメラ情報プッシュ**

- 新メッセージ「カメラ情報プッシュ」を追加する。ペイロードは配列 `[{serial, model, ip, online}]`。送信は `role/phone`、受信・既知テーブル反映は `role/edge`。  
- 送信タイミングは、撮影開始要求時・撮影開始待ちの間・NOTIFYでオンライン化した時点(いずれも任意時点)。  
- オフライン化の通知は選択(エッジのNOCAMERA表示を速めたい場合に送る)。  
- JSON key はデータ構造仕様書(43)の規約に合わせる。  

### **5.2 本人確認(両役割共通)**

- 接続後に `deviceinformation` で `(model, serial)` を確認し、両方一致で採用する。IPはヒント。  
- 既存の「serial 一致のみの枝」(holyGrailEntity.cpp の startSessionSequence / setReconnect)は、model 一致を AND で追加して締める(現状の穴)。  

### **5.3 エッジの発見フォールバック順(STA・スマホ不在)**

前回IP＋検証 → M-SEARCH 1発 → 限定サブネットのバッチ探索(実在ホストのみ:8080)＋検証。AP時は `apClientIps` で置換する。  

### **5.4 スマホのプレゼンスマップ実装要件**

- Android は MulticastLock 保持(NOTIFY受信に必須)とフォアグラウンドサービス(アプリ生存中はマップ維持)を要する。アプリ失効時はマップも失効し、再起動時に M-SEARCH で再構築する。  
- 失効管理は `last-seen` ＋ TTL ＋ 定期M-SEARCH。presence と owned を分離する。  

## **6. 移行方針**

- 発見の低レベル(deviceDiscovery::search / detectSsdpBase / cameraController / connectManual / apiCanonCCAPI)は `10_common` に残す(両役割が使う素材)。  
- 高レベルのオーケストレーションのみ `30_role` へ移す(スマホ=マップ＋プッシュ、エッジ=既知テーブル＋フォールバック)。実際に割れる層は薄い。  
- ネットワーク下層の口(`net::`)に、必要に応じ `multicastHold` / `release`、`ssdpListen*`(既存)等を整理する。  
- 今回追加した診断ログのうち、`THREADdiag`(xTaskCreate 失敗検出)は恒久で残す。`DETdiag` / `ESTdiag` / `LOOPdiag` / `SEQdiag` は安定後に除去または `_DEBUG` ゲート化する。  

## **7. 未決事項**

- 受動NOTIFYの取りこぼし率を実機計測する(カメラを offline→online し、エッジが拾うまでの時間で「賭けてよい層か」を判定)。  
- 発見結果の共有方式(single-flight / 短命キャッシュ)の粒度。両経路(M-SEARCH / AP-probe)を同一の共有スナップショットに載せるか。  
- 「待機中はカメラを占有しない」への整合。現状は開始操作時に即 establishSession(ライブビューON)で掴む。発見(在/不在確認)と占有(撮影窓入場で確立)を分離する余地がある。  
- iPhone のマルチキャスト受信の entitlement / API 差を `platform/30_iPhone` に閉じ込める。  
- 本方針を 47. モジュール構造仕様書 / 43. データ構造仕様書(ETPメッセージ)へ反映する。

## **9. 実装状況・検証記録(2026.07.06)**

branch `fix/edge-msearch-retry-drop-knownip`(未コミット)。実機: R10(.10) + R100(.9) + Edje00/Edje01 + Android。

### **9.1 実装した項目**
- **P1 本人確認(model+serial)厳格化**: `startSessionSequence` / `setReconnect` のカメラ選択に model 一致を AND 追加(serial のみ→ (model, serial) 両方一致)。**実機で検証済**(R100 が serial 一致で確立、誤採用なし)。
- **P2 ETP `C_CAMERA_INFO=10`**: スマホ→エッジのカメラ情報プッシュ。`etp.h` / 送信 `edgeClient.cpp`(`nativeEdgeCameraInfo`) / 受信 `etpEdge.cpp`→`hge_setKnownCameras`。**実機で受信検証済**(`rx cmd=10`、既知テーブル total=2)。
- **P3 エッジ IP直結優先+フォールバック**: `startSessionSequence` を「IP直結+本人確認 → 不発時のみ SSDP M-SEARCH」に再構成(§3.3.1)。既知IP(スマホプッシュ)→ `connectManual` → (model, serial) 検証で採用し **SSDP を省略**。serial 確定は直結、機種のみ指定は「機種一致がオンライン1台」の曖昧さ無しケースのみ直結(複数同機種はSSDPへ委ねる)。**実機で検証済**: クリーン開始で `IPDIRECTdiag serial-hit ip=192.168.1.9`、**M-SEARCH 0回**で establish→CAPTURING(3/480 枚)。
- **P4(簡易)スマホ プッシュ**: `startOnEdge` が開始前に `nativeSearchDevicesList()`(スマホ側SSDPは信頼できる)で発見→`(serial, model, ip, online)` をエッジへプッシュ。**低速で不安定な発見をスマホに寄せ、エッジは高速なIP直結に徹する**という本設計の核が、常駐プレゼンスマップ(§5.4)未実装でも成立することを実証。

### **9.2 実装中に判明した要点(重要)**
- **メーカー名表記の不一致**: SSDP(UPnP記述子)由来の `manufacturer` は `"Canon"` だが、CCAPI `deviceinformation` 由来は `"Canon.Inc"`。`stripMaker` は前者しか剥がせず、IP直結(=CCAPI経由)で得た device の型番照合(`cameraModelMatches`)が失敗して直結が空振りしていた。`stripMaker` に「メーカー先頭英数字ランと model 先頭語の一致で1語剥がす」フォールバックを追加して解消(`dataManager.cpp`)。これは所持/マスタ照合全般に効く根治。
- **計画カメラは型番のみ**(`pc.name="EOS R100"`)で保持。プッシュ/接続後の device.model は全体(`"Canon EOS R100"`)。両者の照合には語境界を考慮した接頭辞一致が必要(`EOS R10` が `EOS R100` に誤一致しない)。エッジ既知テーブル照合用に `knownModelMatch` を追加。
- **計画は owned カメラの serial を保持している**(`hge_setPlanCamera` が owned 構造体をコピー)。よって serial 確定の直結が主経路になる。
