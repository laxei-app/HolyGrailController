# スマホ内蔵カメラ対応の設計

2026-09-05 検討 / ブランチ `feat/builtin-camera`

---

## 1. 何をするか

スマホに内蔵されているカメラを、キヤノン機と同じように撮影計画から使えるようにする。

1. **内蔵カメラを自動的に登録する** — 複数のカメラを持つ端末では、それぞれを別のカメラとして扱う
2. **`detectBuiltin` / `apiBuiltin` を新設**し、キヤノン機との違いをそこで吸収する
3. **露出の変化量の制限を「1コマあたりの段数」から「1秒あたりの段数」へ変える** — 共通部分に入る唯一の変更

---

## 2. 足場は既にある

`detectBase.h` に、この拡張を見越した記述が既に入っている。

```
//  ・Canon CCAPI     : detectCanonCCapi (SSDP系: detectSsdpBase を継承)
//  ・Sony/Nikon/内蔵 : 将来 backend を追加(本改修外・構造のみ)
```

使えるもの:

| 仕組み | 場所 | 内蔵カメラでの使い道 |
|---|---|---|
| `detectBase` / `apiBase` の抽象 | `10_common/src` | そのまま実装する |
| バックエンドの一覧 | `cameraController::backends()` | ここへ足す |
| Entity から Java を呼ぶ経路 | `20_platform/20_Android/src/edgeClient.cpp` の `bleExchange` の形 | Camera2 を叩く |
| スマホ限定の実装の置き場 | `30_role/10_phone/src/skySim.cpp` の前例 | 役割で分ける前例 |

`apiBase` は**測光の手段まで実装側に隠す**設計になっており、`captureRunner` は結果の `sceneRef` しか見ない。
「別メーカー/別方式のカメラを足すときは meterScene/meterHere/meterTimingHint を実装するだけでよく、
captureRunner には一行も手を入れない」とヘッダに明記されている。この前提は今回も守る。

## 3. 置き場所

内蔵カメラは Android 固有なので、**共通部分には置かない**。

```
40_src/20_HolyGrailEntity/20_platform/20_Android/src/
    detectBuiltin.cpp / .h      端末内のカメラを列挙する
    apiBuiltin.cpp   / .h       Camera2 を Kotlin 経由で叩く薄いブリッジ
40_src/10_UI/20_Android/
    BuiltinCamera.kt            Camera2 の実装本体(撮影・設定・画像の取り出し)
```

### 共通部分がプラットフォーム層を知らずに済ませる

`cameraController::backends()` は `10_common` にあるので、そこから Android 固有のクラスを
`#include` してはいけない（エッジのビルドが壊れる）。**登録の口**を1つ足す。

```cpp
// cameraController に追加
static void addBackend(std::unique_ptr<detectBase> b);
```

Android の初期化（`jniBridge` の `hge_init` 経路）から1回だけ呼ぶ。エッジ側は呼ばないので、
エッジのバイナリには内蔵カメラのコードが1バイトも入らない。

## 4. detectBuiltin

「検出」がネットワーク探索ではなく**端末内の列挙**になる点だけが他と違う。

| メソッド | 中身 |
|---|---|
| `detect()` | `CameraManager.getCameraIdList()` を列挙。`want` が来たら合致した1台だけ作る |
| `identify()` | `detect()` と同じでよい（認証も締め出しも無いので、叩いて害が無い） |
| `identifyAt()` | 非対応（IP の概念が無い） |
| `makeManualDevice()` | 非対応 |
| `watchStart()` / `watchStop()` | 不要（出現・消失が無い） |

### 対象は物理カメラだけ

論理カメラ（複数の物理カメラを束ねたもの）は出さず、**物理カメラだけ**を1台ずつ出す。
広角・超広角・望遠がそれぞれ別のカメラとして一覧に並ぶ。

### serial の作り方

所持カメラは serial で一意に管理されるので、ここが安定していないと起動のたびに増える。

```
BUILTIN:<cameraId>
```

端末をまたぐことは想定しないので、カメラ id だけで足りる。将来ひとつのスマホの設定を
別のスマホへ移すことがあれば `BUILTIN:<端末の安定ID>:<cameraId>` へ拡張できる形にしておく。

### 機材マスタに載っていない問題は自動的に解決する

キヤノン機では、機材マスタに無い機種のセンサー実寸と画素数を「撮った画像の EXIF から埋める」
(`readSensorSpec`) 必要があった。内蔵カメラは `CameraCharacteristics` から

- センサー実寸 `SENSOR_INFO_PHYSICAL_SIZE`
- 画素数 `SENSOR_INFO_PIXEL_ARRAY_SIZE`
- 焦点距離 `LENS_INFO_AVAILABLE_FOCAL_LENGTHS`
- 絞り `LENS_INFO_AVAILABLE_APERTURES`

が**検出の時点で**取れる。撮る前から NPF も撮影シミュレーションも出せる。

### 表示名

機種名とレンズの区別が人に分かる形にする。焦点距離から「広角 / 超広角 / 望遠」を当てる。

```
name         = "Pixel 6 広角"
assignedName = "BUILTIN_0"
```

Pixel 6 で実装・検証するが、**特定の機種に依存する分岐を書かない**。取れなかった項目は
空のままにして落ちないようにする（端末によって `CameraCharacteristics` の欠けは普通にある）。

## 5. apiBuiltin

| 項目 | 内蔵カメラでの実現 |
|---|---|
| ISO | `SENSOR_INFO_SENSITIVITY_RANGE`（整数の範囲） |
| SS | `SENSOR_INFO_EXPOSURE_TIME_RANGE`（ナノ秒・連続） |
| F値 | `LENS_INFO_AVAILABLE_APERTURES`。多くの端末で1点のみ |
| 撮影 | `CONTROL_AE_MODE_OFF` + `SENSOR_SENSITIVITY` / `SENSOR_EXPOSURE_TIME` |
| 記録形式 | **JPEG のみ** |
| 測光 | 撮った画像から。ローカルなので取得が速い |
| `meterTimingHint` | `afterShutterClose = true`（撮影画像フィードバック系） |
| `readDeviceStatus` | 空き容量・電池・温度をスマホから取る |
| `readSensorSpec` | `CameraCharacteristics` から即答（EXIF を待たない） |
| `keepAlive` / `setupShootingModeManual` / `restoreShootingMode` | 実質 no-op |
| `setMeterLv` | 区別を持たないので何もしない |

### 測光で楽になるところ

CCAPI 実装が苦労していた点の多くが消える。

- 「新しい画像の登録通知を待つ」が要らない（撮った結果がその場で手に入る）
- 記録中のファイルを掴んでしまう問題が無い（R10 が固まる原因だった）
- サムネイル取得回数の上限が無い（R10 は電源投入あたり 200 回程度で応答しなくなる）
- 認証も 403 締め出しも無い

そのため `meterLv`（ライブビュー主体の逃げ道）は要らない。

### 将来の動画の自動生成

JPEG のみで始めるが、**将来 DNG を足すときも JPEG は同時に出す**。ヒストグラムの取得に
JPEG を使っており、動画の自動生成にも連番 JPEG が要るため。

## 6. 露出の目盛り — 合成する

### 現状

露出は「カメラの設定値の文字列」のリストで持ち（`hgc::camera::isoList` / `ssList`）、
`expo::exposureCtl` は各軸を**テーブルの1目盛り**単位で動かす（`ladder` + `idx`）。

### 方針

内蔵カメラでも**目盛りを合成する**。ISO と SS の範囲から刻みを作って
`isoList` / `ssList` に載せれば、既存の仕組みにそのまま乗る。

連続値をそのまま扱えるようモデルを拡張する案は採らない。`applyStops` / `stepAxis` /
`stepHome` / 限界の判定 / ログ / 解析スクリプト / UI / 機材マスタ / エッジのすべてに波及し、
得られるものに対して代償が大きい。

### 刻みは 1/3 段より細かくする

スマホのカメラは連続に設定できるので、その性能を活かして**1/3 段より細かい目盛り**にする。
ただし刻みは開発の状況で変える可能性があるものとして扱い、**1か所で変えられるようにする**。

```cpp
// apiBuiltin の中の1か所
constexpr double kBuiltinStepStops = 1.0 / 6.0;   // 目盛りの刻み[段]
```

### 共通部分への波及: 「1歩」はカメラごとに違う

これに伴い、**`kExposureStepStops = 1/3` という固定の前提を外す**必要がある。

現在この定数を使っている箇所:

| 使い道 | 場所 | 直し方 |
|---|---|---|
| デッドバンドの判定 | `wouldOvershoot()` | そのカメラの1目盛りを使う |
| 何目盛り踏むかの決定 | `stepsToClose()` | 同上 |
| ヒステリシス帯の下限 | `effHysteresis()` | 同上（帯が1歩より狭いと必ず往復する、という理屈は変わらない） |
| 1コマの上限 | `kMaxCatchUpStops` | §7 の速度制限へ置き換える |

`expo::exposureCtl` は各軸の `ladder` を持っているので、そこから
**「いま踏める最小の段差」**を返す口を足すのが素直。

```cpp
// exposureCtl に追加
double minStepStops() const;   // 現在位置の周辺で1目盛り動かしたときの段差
```

軸ごとに刻みが違う（ISO は 1/3 段、SS は 1/6 段、など）場合も、これなら自然に扱える。

## 7. 変化速度での制限

### 何を変えるか

いまは `kMaxCatchUpStops = kExposureStepStops` で「**1コマあたり最大 1/3 段**」。
これを「**1秒あたり最大 N 段**」に変える。

```
上限        = 0.0222 段/秒   (= 1/3段 ÷ 15秒)
1コマの許容 = 上限 × 前のコマからの経過秒
```

### なぜ変えるか

1分周期のような**今までテストしていない長い撮影周期でもうまく動くようにするため**。
長い周期では1コマあたりもっと大きく露出を動かす必要があり、この形なら自動的に対応できる。

| 撮影周期 | 1コマの許容 | 今までとの違い |
|---|---|---|
| 9秒 | 0.20段 | **今より遅くなる**（今は 1/3 段動ける） |
| 15秒 | 0.33段 | **完全に同じ**（これまでのテスト結果がそのまま生きる） |
| 30秒 | 0.67段 | 速く追える |
| 60秒 | 1.33段 | 速く追える |

9秒周期が遅くなる点は承知のうえで採用する。**そのほうがよく撮れると分かれば速度制限を調整する**。

### 目盛りが粗いカメラのための「貯金」

1コマの許容が1目盛りに満たないとき（9秒周期・1/3段刻みのカメラなら 0.20段 < 0.333段）、
そのままだと永久に動けない。**許容量を貯めて、1目盛りぶん貯まったら動かす**。

```
budget += 上限 × 経過秒
1目盛り動かしたら budget -= その段差
```

9秒周期なら 2コマで 0.40段 貯まり、3コマ目までに1目盛り動く。平均すれば狙いの速度になる。

### 適用する範囲

| 場面 | 速度制限 | 理由 |
|---|---|---|
| 撮影中の定常追従 | **適用する** | 本来の目的 |
| 窓の切り替え（自動露出→自動露出の目標移行） | **適用する** | 長い周期に耐えさせるため |
| つなぎ目の寄せ（境目で画質の配分を寄せる） | **適用する** | 同上 |
| 夜間露出への収束 | **適用する** | 同上 |
| 初期収束（シャッターを切る前） | **適用しない** | 撮影前なので速く詰めてよい |

現在これらはすべて「1コマ 1/3 段」で書かれている（`captureRunner.cpp` の 1391 / 1425 /
1620 / 1643 行あたり）。

**特に注意が要る箇所**: 夜間露出への収束は「残りフレーム数が、現在→夜間の所要フレーム数
(1/3段/枚) 以下になったら測光を止めて寄せ始める」という判定を持つ。速度制限を入れるなら
**この所要フレーム数の計算も同じ式にしないと、窓の終端できっかり着地しない**。
つなぎ目の寄せも「終端で厳密に一致させる」ことが要件なので同様。

### 値の持ち方

**定数**にする。天候の変化や太陽の動きという自然現象で決まるものであり、
撮影制御方法ごとに変える性質のものではない。

ただしテストの状況で調整するので、**1か所で変えられるようにする**。

```cpp
// captureRunner.h — 露出の変化速度の上限はここだけで決める
static constexpr double kMaxExposureRateStopsPerSec = (1.0 / 3.0) / 15.0;   // 0.0222 段/秒
```

## 8. 撮影計画と外部端末の関係

内蔵カメラは**そのスマホの中にしか無い**ので、外部端末へ送った計画では使えない。

- 内蔵カメラを選んだら、端末の選択肢は「スマホ」だけにする
- **端末が自動的に「スマホ」へ切り替わる**ようにする（選べなくして戸惑わせるより素直）
- 外部端末を選んでいるときは、カメラの選択肢に内蔵カメラを出さない

エッジ側は内蔵カメラのコードを持たないので、万一送られても `apiBase` を作れず失敗する。
UI で送らせないのが本筋。

## 9. エッジ端末への影響

| 変更 | エッジへの影響 |
|---|---|
| `detectBuiltin` / `apiBuiltin` | **無し**（Android のプラットフォーム層にあり、リンクされない） |
| 目盛りをカメラごとに扱う | 有り（`exposureCtl` / `captureRunner`）。ただしキヤノン機は 1/3 段のままなので挙動は変わらない |
| 変化速度での制限 | **有り**。15秒周期なら挙動は同じだが、短い周期・長い周期では変わる |

共通部分に手を入れるので、**3ターゲット（CoreS3 / StickS3 / Android）のビルドと通し検証が要る**。

## 11. 決めたこと（2026-09-05 ユーザー回答）

- 目盛りは**合成する**。ただし 1/3 段より細かくし、刻みは変更できるようにする
- 速度上限は**短い周期にも適用**する。値は調整できるようにする
- 速度上限は**定数**。ただし1か所で変えられるようにする
- 対象は**物理カメラだけ**
- 記録形式は **JPEG のみ**。将来 DNG を足すときも JPEG は同時に出す。動画の自動生成も視野
- 実装は **Android のフォルダ**に置く
- Pixel 6 で実装・検証するが、**他の Android 端末でも動くことを意識する**
- 速度制限は**窓の切り替え・つなぎ目の寄せにも適用**する。初期収束は適用外
- 内蔵カメラを選んだら**端末は自動的にスマホへ切り替える**

## 13. 加算で作る長秒露光（2026-09-06 決定・実装済み）

### 何のために
星をきれいに撮るには 20〜48 秒の露光が欲しい。しかしセンサー1コマの露光には上限がある
（Pixel 6 広角 8.3 秒、超広角 16.2 秒。Camera2 の `SENSOR_INFO_EXPOSURE_TIME_RANGE`）。
1コマでこれを超える手段は無い。

### どうするか
- 上限以下のコマを**続けて撮り、RAW（Bayer）を線形の画素値で足す**。三脚固定なら、星の流れ方も
  光子の総量も本物の長秒露光と同じ（読み出しノイズだけ √N 倍。夜空ではショットノイズ支配なので効かない）。
- JPEG は階調カーブ済みの 8bit で暗部が潰れているので足せない。RAW は線形で 10bit 以上ある。
- 現像は **2×2 束ね**だけ（4080×3072 → 2040×1536）。最終成果物は 1920×1440 の動画なので足りる。
  デモザイクが要らず、ノイズもさらに半分になる。ホワイトバランス・色行列・黒レベル・周辺減光の地図は
  撮影結果（`CaptureResult`）が返す値をそのまま使う。
- **1コマで足りる露光でも同じ道を通す**。コマ数で経路が変わると、境目で色や階調が跳んで動画に段差が出る。
- RAW を出せない端末（または Bayer でない端末）は従来の JPEG に落ち、上限はセンサーのまま。

### 露出モデルへの載せ方
- apiBuiltin の合成 ss 目盛りの上端を「センサーの上限」ではなく **48 秒**にする（`kMaxStackSsSec`）。
  センサーの上限が何秒でも、内蔵カメラは 48 秒まで設定できる（ユーザー決定）。
- 上限を超える ss は `shootStart` の中で N = ceil(ss ÷ 上限) コマに等分し、バーストで撮って足す。
  上位（露出制御・測光・計画）から見れば長い ss があるだけで、**Entity 側の変更はほぼ無い**。
- 測光は出来上がった1枚（加算後）を見るので、明るさは仮想 ss に対応する。

### 最小周期
- 内蔵カメラは **1.25 × 最長 ss** を最小周期とし、それ未満は設定できない（ユーザー決定 2026-09-06）。
  8.3 秒→10.4 秒（従来 ss+2 とほぼ同じ）、24 秒→30 秒、48 秒→60 秒。
- 露光の後に加算・現像・JPEG 化（実測 0.6〜0.9 秒）と測光が続くための余裕。
- 既存の仕組み（UI は最小未満を受け付けない／Entity は周期を自動で伸ばす）にそのまま乗せた。

### ひな形の初期値
- 夜間の固定露出は **24 秒に近い目盛り**（F1.9 ISO1600 24 秒 ≒ 一眼の F2.8 ISO3200 20 秒）。
  48 秒は明るい空では飛ぶので初期値にはしない。周期 30 秒 = 1.25 × 24 とも合う。

### 熱
- `PowerManager` の熱状態（NONE…SHUTDOWN）を 5 分ごとの状態確認（`readDeviceStatus`）に乗せ、
  変化したときログに残す。SEVERE 以上で高温警告、EMERGENCY 以上で「撮影できない」として通知する。
- 加算のコマ数を自動で減らす等の逃げ道は、実測（一晩のログ）を見てから決める。

### 実測（2026-09-06 室内・Pixel 6 広角）
- 1/60 秒×3 コマの和と 1/20 秒×1 コマの明るさが一致（平均 RGB 90.9 vs 90.8）。加算は線形に正しい。
- 8 秒×3 コマ（仮想 24 秒）を周期 30 秒で 6 コマ、シャッターの遅れ 0〜1ms。現像 0.86 秒。
- 熱状態 0（平常）のまま。夜空の実写はこれから。
