■ソフトウェア構造
　ほとんどのロジックを rust で書いて共通のコードとしたい。
　理想的には UI は言われたことをするだけ。
　ボタンを有効にするとか表示するとか、言われた図形を表示するとか。
　どこを押されたかを通知するとか、 UI は最小限にしたい。

◎インターフェース
・UI からアクション通知
・ライブラリからの通知を受け取る

　以上のインターフェースが必要。
　いずれも、devideiocontrol 方式で
　・機能コード
　・in パラメータ
　・out パラメータ
　とするのが汎用的でいいかな。

　受け取る側のコードも android/swift で異なる。
　なるべく共通にしたいが…。
　
◎その際の UI とのインターフェースをメッセージでおこなう形式とするのが疎結合で良いのかも。
　UI から関数を登録しておいて受け取った id に応じたメッセージを自分自身に投げる。
　スレッドやタスクの扱いが OS によって異なるが基本的には、
　・UI のスレッドと
　・カメラ制御のスレッド
　が必要と思われる。

◎OS に依存するコードは UI 部分にまとめる。
　スレッドとかね。
　LAN 関係の api は rust 側で意識せずに書いてもビルドすればそれぞれで
　動くコードになるらしい。

◎明るさの決定
【live view】
　canon はヒストグラムが取れる。
　画像ではなくヒストグラムから判断した方が早いしデータ量も少ない。

　しかし、sony はヒストグラムを取得する方法が無い。
　live view からヒストグラムを作りインターフェースを合わせるか。
　api のインターフェースとしては、
　・live view 取得
　・ヒストグラム取得
　の両方を用意しておく。
　sony は内部的には live view からヒストグラムをつくる。

【撮影済み画像】
　live view はセンサーのデータを送ってくるだけなので8秒露光とかした
　際の画像の明るさとは違う、だいぶ暗いものになる。
　撮影済み画像のサムネイルかディスプレイ用の画像で解析した方が良い。
　・サムネイル    160×120px　　　数KByte
　・ディスプレイ用1620×1080px　　数百KByte
　・生データ                  　　数十MByte

【明るさに関する設定】
　iso,f値、ss は明るさに対応した log2 をベースにした変数に置き換える。
　通常のステップは
　・iso 2倍に比例、2倍で 1 ステップ
　・ss  2倍に比例、2倍で 1 ステップ
　・f値 √2 倍に比例 √2倍で 1 ステップ。
　設定できるこれらの値を配列に持って、対応する明るさ(APEX システム）の数値を
　持たせる。明るさの計算はこの APEX システムの数値を使って計算する。
　ヒストグラムはiso,ss,f値の反映された物で取得するので今のこの明るさに対して
　どのくらい暗くするか(もしくは明るくするか)を APEX システムの数値で決める。
　通常は1段どれかのパラメータを変更するだけである。
　1/2、1/3段の設定もできる。
　1段を 6 にすれば 1/2 も 1/3 も整数で置き換えられるので便利かも。
　一番暗いのは iso 100、ss 1/16000、f 16 とか。そのカメラで最も暗い設定を 0 にして
　1段上がった数値は +6、1/2 なら +3、1/3 なら +2 にすればすっきりする。
　数値は相対的なものなので始まりはどこでもいいでしょう。
