# カメラ方式の拡張に向けた構造修正 — 優先度と進め方（2026-09-06）

対象: 「カメラ固有処理の共通部への漏れ 洗い出し」（同日）の A〜D 23 件 ＋ カメラの性質（レンズ固定など）をマスタから持たせる件。
方針: 一つ直すごとにビルド（Android ＋ エッジ 2 機種）と実機テストで確かめてから次へ。
判断の軸: (1) 次のカメラ／iPhone を足すとき手戻りになるか (2) いま動いているものを壊す危険 (3) 変更の大きさ。

---

## 基本設計（先に決めておく 2 点）

### ① カメラの性質は「カメラの記録」に持ち、出所は 2 つ

| 性質 | 意味 | 出所 |
|---|---|---|
| `lensFixed` | レンズ交換不可（計画・所持カメラでレンズを変えない） | マスタ（`lens_fixed`）／api 実装（`fillCameraProfile`） |
| `localOnly` | 撮影できるのはこの端末だけ（外部端末に送れない） | api 実装のみ（端末の中に居るかは機材ではなく接続の性質） |
| `noSyncShot` | 同期撮影に参加できない | api 実装（当面）。将来マスタでも可 |
| `readOnly` | 利用者が所持カメラの欄を編集できない | api 実装のみ（「端末が答える値だから直させない」という運用の性質） |
| `intervalFactor / intervalMargin` | 最小周期の規則（既に実装済） | api 実装 |
| `meterLv` → `meterMode` | 測光の方式（既存。名前を方式非依存に） | マスタ（`meter_lv` を残しつつ `meter_mode` へ）／所持カメラで上書き |

- **マスタで持つのは「機材として決まっている性質」**（レンズ固定・測光の既定）。
- **api 実装で持つのは「接続や実装の性質」**（この端末でしか撮れない・同期不可・編集不可・周期の規則）。
- どちらも所持カメラ登録時に `hgc::camera` の欄へ写し、以後 UI と Entity は欄の値だけを見る（`BUILTIN:` 判定を消す）。
- マスタは `30_refer/10_機材マスター/*.json` と公開リポジトリ `hgc-master/master/` の両方。**hgc-master は指示があるまで更新しない**（既定）。
  新しい欄は「無ければ既定値」で読むので、古いマスタでも壊れない。

### ② 共通部分の「接続先」は不透明にする

- `device.urlAccess` に URL を入れる約束を「宛先（文字列。中身は api 実装だけが読む）」に改める。
  IP や URL が要る処理（AP 離脱の突き合わせ・表示・ログ）は apiBase に聞く（`linkKey()` / `endpointText()`）。

「段」= 実装・テストの単位。段の中は同時に直してよい（同じ場所を触るため）。

## 進め方の約束

- 段の順に進める。各項目は「変更 → Android ＋ CoreS3 ＋ StickS3 ビルド → 単体テスト → 実機（該当する組み合わせ）」で締める。
- 共通部分に触る項目（第 1・2・3 段）はエッジへの書き込みまで行って確かめる（キヤノン機の動作が主対象）。
- hgc-master（公開マスタ）の更新は、第 2 段でマスタ形式が決まった後、指示を受けてから。
- 内蔵カメラの夜空実写（画質・薄明追従・熱）は構造修正と独立なので、晴れた晩に並行して行う。

## 見送る／しないこと

- 露出の文字列表現（"1/4000" 等）は汎用のまま使う（内蔵で困らなかった。変えると計画・ログ・解析まで及ぶ）。
- `httpAuth`（ダイジェスト認証そのもの）は HTTP の規格なので共通に残す。
