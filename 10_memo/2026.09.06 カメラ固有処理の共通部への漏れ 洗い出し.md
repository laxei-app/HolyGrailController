# カメラ固有処理の共通部への漏れ — 洗い出し（2026-09-06）

## 目的

今後、別の制御方式のカメラ（ソニー・ニコン等）や iPhone を実装するときに障害となる
「キヤノン CCAPI 固有の知識が apiCanonCCAPI / detectCanonCCapi の外に置かれている箇所」を
洗い出す。対象は 10_common・30_role・20_platform・10_UI（Android / M5）。

## 構造の現状（先に結論）

骨格は正しい。露出・測光・センサー諸元・撮影モード・接続維持・在否は
`apiBase` / `detectBase` の仮想関数を通っており、内蔵カメラ（apiBuiltin）が
共通部分を触らずに乗った実績がその証拠。

漏れているのは **「HTTP で話す・URL がある・応答本文に理由が書いてある・
シャッター速度は 1/N か秒」といった *CCAPI の世界観* が共通の型と関数に染み込んでいる**
こと。次のカメラが同じ世界観（HTTP + SSDP + 数値文字列）なら困らないが、
iPhone（AVFoundation）や USB/BLE のカメラでは邪魔になる。

## 漏れの一覧（重要度順）

### A. 共通部分が CCAPI の「言葉」を直に使っている（必ず直す）

| # | 場所 | 内容 | あるべき姿 |
|---|---|---|---|
| A1 | `presenceMonitor.cpp` greetLocked | 挨拶の URL `access + "/ver100/deviceinformation"` を直書き。401/403 の解釈（資格情報が無ければ 1 回でやめる／403 は締め出し）もここ | `apiBase::greet()`（または detectBase）にする。共通は「挨拶を頼む→成否と『もう頼まない』の指示」だけ受ける |
| A2 | `captureRunner.cpp:394` fireShutter | `status == 503 && body に "Can not write to card"` でカード起因を判定。HTTP の状態と CCAPI の本文文言 | `apiBase::actShutter` が **意味**（`shutterResult{ok, mediaBlocked, linkLost}`）を返す。共通は文字列を見ない |
| A3 | `captureRunner.cpp` withHttpDetail / `netThread::lastHttpFailure` | エラー文言に「http=応答なし/503」を付ける。HTTP 前提 | `apiBase::lastFailureDetail()` に置き換え。文言はカメラ実装が作る |
| A4 | `deviceDiscovery.h` | `#include "apiCanonCCAPI.h"`（使っていない）。汎用の SSDP ヘルパがキヤノン API に依存 | include を消す。`deviceDiscovery.cpp` のコメントの canon 例は残してよい |
| A5 | `device.h` `enum apiClass { NON, CANON_CCAPI, SONY_DI }` | 共通の型にメーカー名。`detectCanonCCapi` は Sony の SSDP 語まで CANON_CCAPI に写像している（行 14） | `apiClass` を捨て、`device.apiBase` の有無と `detectBase` の所属で判断する。Sony の写像は削除 |
| A6 | `cameraController.cpp:3,26` | 既定の探索元として `detectCanonCCapi` を共通が include して登録 | 登録は役割側（30_role or 各成果物の init）へ。共通はバックエンドの型を知らない（内蔵は既に jniBridge から addBackend している＝この形） |

### B. 共通の「型」が HTTP/SSDP 世界を前提にしている（次のカメラの方式次第で直す）

| # | 場所 | 内容 | あるべき姿 |
|---|---|---|---|
| B1 | `device.h` | `uuid / location / urn / service / urlbase / urlAccess` は全部 UPnP の項目。内蔵カメラは urlAccess に「論理/物理」を無理やり入れている | 発見の元データは `detectBase` 派生の私有に。`device` は `model / serial / assignedName / manufacturer / apiBase` と **不透明な接続キー**（文字列）だけにする |
| B2 | `captureRunner.cpp` `hostOfUrl(dev_->urlAccess)` `linkDown::generation(camIp)` | IP を取り出して AP の離脱イベントと突き合わせる。IP 前提 | `apiBase::linkKey()`（不透明）と `apiBase::linkAlive()` に。AP 離脱は platform/edge 側が linkKey で通知 |
| B3 | `holyGrailEntity.cpp` hostFromDevice、ログの `ip=?`、`searching camera (direct ip -> ssdp)` | IP と SSDP を前提にした表示・ログ | 表示は `apiBase::endpointText()` のような「人に見せる接続先」を実装が返す |
| B4 | `presenceMonitor.cpp` 全体 | `location`（記述URL）への GET で生死確認、`M-SEARCH` 周期、`hostOf` | 在否の**方法**は detectBase へ（`detectBase::presence` は入れた。生死確認・復帰・挨拶も同じ場所へ寄せる）。共通は表と TTL だけ |
| B5 | `roleDiscovery.h` / `edgeKnownCameras.cpp` | `:8080` のサブネット探索、`[{serial,model,ip,online}]` の IP 前提の既知テーブル | tier3 探索は detectBase の `sweep()` に。既知テーブルの ip は不透明キーに |
| B6 | `httpAuth`（候補の配布 `setCandidates`、`anyRefused/anyUnauthorized` から notice 63/64/65 を作る） | ダイジェスト認証は HTTP の規格だが、**「所持カメラの authUser/authPass = HTTP ダイジェスト」という結び付け**と、その失敗を通知コードへ変換する処理が holyGrailEntity にある | 資格情報は `hgc::camera` に残してよい（汎用）。「どう使うか」と「失敗の意味」は apiBase（`authState()`）が答え、共通はコードに写すだけ |

## 直す順番の提案

1. **A（6 件）** — 共通部分から CCAPI の言葉を消す。エッジのビルドに触るのは今回だけ。
   A2/A3 は apiBase の戻り値の型を 1 つ足す変更なので、apiCanonCCAPI の中で吸収する。
2. **D1/D2** — UI の内蔵判定を Entity への問い合わせに置き換える（iPhone 対応で必ず要る）。
3. **B** — 次のカメラの方式が決まってから。HTTP+SSDP のカメラ（ソニー・ニコンの多く）なら
   B は当面そのままでも動く。iPhone（内蔵）は B1〜B4 を素通りできる（既に内蔵で実証）。
4. **C** — 語彙の整理。害は小さいので折を見て。
